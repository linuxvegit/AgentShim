# v0.6.1 design spec — P04 closure & disciplined core unfreeze

**Status:** Approved 2026-05-13. Implementation pending.
**Source release:** v0.6.0 (master HEAD `b90b7f3`).
**Author:** v0.6.1 brainstorm session, 2026-05-13.

## 1. Goals

v0.6.1 is a follow-up release that pays down the five P04-deferred
Minor items registered in
[ADR-0006](../../adr/0006-cost-aware-routing.md) lines 188-242. Two
items (M-6 derive macro, M-8 model-aware image estimation) are
non-mechanical and worth doing properly; three (M-2, M-3, M-7) are
mechanical or contract-hardening cleanups.

v0.6.1 also lifts the frozen-core invariant on `crates/core/` under
explicit discipline rules — mirroring what Phase 6 §2.2 did for
`providers/src/` — to host one new trait. This sets the precedent for
how future phases may legally extend `core`.

### 1.1 The five closed items

| Minor | Item | Plan |
|-------|------|------|
| **M-2** | Cost-estimator encoder-fallback variants under `#[allow(dead_code)]` | P01 |
| **M-3** | Helper duplication between `cost_filter.rs` and `cost_estimate.rs` | P01 |
| **M-6** | Prometheus metric registration: each new metric requires appending to two array sites | P02 |
| **M-7** | Per-position policy-vec uniformity assumption + survivor-realignment | P03 |
| **M-8** | Non-text content blocks ignored by cost estimator (image/tool/reasoning) | P04 |

### 1.2 Non-goals

The following are explicitly out of scope and remain v0.7+ candidates:

- Realised-cost EWMA tracking (rolling window over observed token usage)
- Distributed cost-filter state (multi-instance shared counts)
- Agent-driven routing preferences (`agent-shim-budget: low` header)
- New providers, new frontends, new frontend protocol features
- Audio / file content end-to-end
- Redacted request/response capture & replay
- k8s manifests / Helm chart

## 2. Frozen-core invariant changes for v0.6.1

The Phase 6 invariant — **empty diff against v0.6.0 baseline for
`crates/core/` and `crates/frontends/`** — narrows in v0.6.1.

### 2.1 New invariant

```
git diff b90b7f3 -- crates/frontends/
```

must be empty. **`crates/core/` is no longer fully frozen.** P04
explicitly adds one new module (`crates/core/src/cost.rs`) and one
new line in `crates/core/src/lib.rs` (`pub mod cost;`).

`crates/frontends/` remains fully frozen — no v0.6.1 plan touches it.

### 2.2 Discipline for the unfrozen `crates/core/`

Lifting the freeze is not a license to refactor. The v0.6.1
discipline is:

- **(a) Trait-only additions.** New `pub trait` items + new `pub enum`
  variants on existing `#[non_exhaustive]` enums are allowed. **No**
  field additions to existing structs, **no** signature changes on
  existing methods, **no** renames, **no** changes to derives on
  existing types.
- **(b) Category tag per hunk.** Each `crates/core/` diff hunk in
  v0.6.1 is classified in the v0.6.1 release notes (CHANGELOG entry
  + P05 PR description) as one of:
    (i) new trait,
    (ii) new enum variant on `#[non_exhaustive]`,
    (iii) new test-only type.
  In v0.6.1 the exhaustive list is fixed by §2.3 — only the items
  enumerated there are permitted; rule (b) is the classification
  scheme any future phase reusing this discipline must follow.
- **(c) Re-state in next phase spec.** The Phase 7 design spec must
  re-state the v0.6.1 baseline (this section) as the new frozen-core
  boundary going forward. v0.6.1 is the new frozen reference, not
  v0.6.0.
- **(d) frontends crate stays fully frozen.** Empty diff on
  `crates/frontends/` since v0.5.0 still holds. v0.6.1 does not
  touch it.

P04's spec-compliance review enforces these rules via:

```
cargo public-api diff --simplified \
  crates/core/ b90b7f3..HEAD
```

(or against the `v0.6.0` tag once applied — `b90b7f3` is the v0.6.0
release commit on master). The diff must show only the additions
enumerated in §2.3, nothing else.

### 2.3 What v0.6.1 legally adds to `crates/core/`

```rust
// crates/core/src/cost.rs (new file, ~50 lines)
pub trait ImageTokenEstimator: Send + Sync {
    fn tokens_for_image(&self, hint: ImageSizeHint) -> u32;
}

/// Per-block size information available to the estimator. The canonical
/// `ImageBlock` does **not** record width/height (see
/// `crates/core/src/content.rs::ImageBlock`), so estimators fall back to
/// vendor-published worst-case defaults when dimensions are unknown.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ImageSizeHint {
    Known { width: u32, height: u32, detail: ImageDetail },
    Unknown,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ImageDetail { Low, High, Auto }
```

```rust
// crates/core/src/lib.rs — exactly one new line
pub mod cost;
```

Nothing else.

that Phase 7+ specs diff against. Phase 7 must re-state the frozen
set on top of the v0.6.1 additions.

## 3. Architecture & crate boundaries

The Phase 6 boundary rules continue:

- **Frontends and providers never import each other.**
- **Router does not depend on observability.** Latency probes are a
  trait defined in `router`; the Prometheus-backed implementation
  lives in `gateway` and is injected at `AppState::new`. v0.6.1's
  `ImageTokenEstimator` follows the same shape: trait in `core`,
  impls in `router`, selection in `gateway`.
- **Gateway is still the sole wiring point.**

### 3.1 New crate: `crates/observability-derive/`

Proc-macro crate that hosts `#[derive(Metric)]`. Standard Rust pattern
(same shape as `serde_derive`, `thiserror`).

```
[lib]
proc-macro = true
```

Dependencies: `syn`, `quote`, `proc-macro2`. Zero workspace deps.

Consumer: `crates/observability/` and only `crates/observability/`.
Other crates depend on `observability`, never on `observability-derive`
directly.

**Boundary rule:** `observability-derive` produces tokens that expand
against types living in `observability`. The derive macro's expansion
is the only place those two crates' name-spaces meet.

### 3.2 `ImageTokenEstimator` placement

- **Trait + `ImageSizeHint` + `ImageDetail`:** `crates/core/src/cost.rs`
  (per §2.3).
- **Three impls:** `crates/router/src/image_estimators/{anthropic,
  openai, responses}.rs`. Each is a unit struct with vendor-specific
  token constants inlined. Each handles `ImageSizeHint::Unknown` by
  returning a vendor-published worst-case token count.
- **Selection:** `crates/gateway/src/state.rs` maps inbound
  `FrontendKind` to `Arc<dyn ImageTokenEstimator>` at request time.

`ResponsesImageEstimator` inherits OpenAI's tile-math (Responses API
is OpenAI-shaped) but exists as its own type for explicit dispatch
and to allow divergence later.

### 3.3 `PolicyVec<T>` (M-7)

```rust
// crates/router/src/policy_vec.rs (new file)
pub(crate) struct PolicyVec<T> { inner: Vec<T> }

impl<T> PolicyVec<T> {
    /// Constructor enforces same-length-as-survivors at the type level.
    /// Mismatched lengths are a compile error at every call site, not
    /// a runtime panic.
    pub fn new(items: Vec<T>, expected_len: usize) -> Result<Self, PolicyVecLenError>;
}
```

Internal-only `pub(crate)`. No new public API on `router`.

### 3.4 Data flow: image-aware cost estimation

```
Inbound HTTP request
  → frontend decode (frontends crate)            [frozen]
  → CanonicalRequest with content blocks         [core: unchanged structs]
  → router::cost_estimate::estimate_request_cost
       │
       └─ image blocks → ImageTokenEstimator     [core: new trait]
                          ├─ AnthropicImageEstimator   [router: new]
                          ├─ OpenAiImageEstimator      [router: new]
                          └─ ResponsesImageEstimator   [router: new]
  → router::cost_filter::filter_chain            [unchanged plumbing]
```

The `ImageTokenEstimator` selection is gateway-side — it knows the
inbound `FrontendKind`. The selection is passed into the router via
the existing constructor wiring (same shape as `PrometheusLatencyProbe`
in Phase 6 P04 T5).

## 5. Sequencing & ordering rules

**Hard ordering:**

1. **P01 first** — pure refactor, smallest risk, lands cleanly on top
   of master `b90b7f3`.
2. **P02 second** — independent of P01 in source-file terms, but
   lands before P03/P04 so the metric-parity baseline is captured
   early and stays stable through the rest of v0.6.1.
3. **P03 before P04** — P04 may consume `PolicyVec<T>` from P03 in
   `resilient_caller.rs` if a natural call-site appears during
   image-estimator wiring. Even if P04 doesn't end up needing it,
   P03's earlier landing isolates its review.
4. **P05 last** — docs reflect the four lands.

**Parallelism allowed:** P01 and P02 can run as parallel worktrees if
useful (no file overlap between them — P01 touches `router/src/`,
P02 touches `observability/src/` + new `observability-derive/`).
P03 and P04 must serialise.

**Verification gates between plans:**
- After every plan: `cargo nextest run --workspace` total pass count
  strictly ≥ previous baseline (671 going in).
- After P02: structural-parity test against v0.6.0 baseline green.
- After P04: `cargo public-api diff --simplified crates/core/` shows
  **only** the §2.3 additions.
- After P04: `git diff b90b7f3 -- crates/frontends/` (or `git diff
  v0.6.0 -- crates/frontends/` once tagged) is empty
  (frontends-still-frozen check).

## 7. Risks & mitigations

| Risk | Likelihood | Mitigation |
|------|-----------|-----------|
